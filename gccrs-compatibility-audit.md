# gccrs compatibility audit

**Snapshot: 21 September 2026.** Repository: `Rust-GCC/gccrs`, checkout and local `origin/master` both at `de2588c201627ca5f95623d78ad1738104833834`. Linux comparison: **7.3-rc4**, commit `93f51579e7df248780214094418f205253383cc5`. Research report; no compiler implementation changes.

## Executive summary

gccrs has substantial implementations of Rust generics, traits, associated types, closures, const evaluation, const generics, argument- and return-position `impl Trait`, generic associated types, dynamic dispatch, coercions, macros, and GCC code generation. Several of these have execution tests, not just parser tests. An independent compiler that supports this much can still fail very early on a kernel build because the kernel needs a particular combination of library contracts, macro imports, host procedural macros, current language details, and build-system integration.

**The evidence supports “a substantial compiler with important semantic and infrastructure gaps,” not “mostly a parser,” and not “nearly a complete Rust implementation.”** The most useful distinctions are between an implemented mechanism with a failing combination, a deliberately narrow implementation, an accepted-but-ignored attribute, and a genuinely absent semantic path.

The supplied repository `core.log` does **not** demonstrate a completed compilation of Rust 1.49 `core`. It contains **902 error diagnostics, one internal compiler error, and 211 warnings**, and stops during type checking while visiting `cmp`. Many errors are consequences of earlier projection, inference, pattern, or method-selection failures. There are also **107 distinct rejected intrinsic names**, including both historical naming mismatches and missing operations. Later type checking, whole-crate code generation, usable metadata, linking, and library correctness remain unproved. There is no defensible percentage-complete estimate.

The effort already extends well beyond the stable Rust 1.49 language. The imported `core/src/lib.rs` names **98 distinct feature gates**, counting conditional/bootstrap alternatives. That is an inventory of library source requirements, **not 98 implemented gccrs features**. Concrete implemented pieces include compiler-recognized lang items, intrinsic lowering, the `rust-call` closure interface, minimum-specialization cases, const generics that stabilized after 1.49, SIMD representation, selected platform intrinsics, and adapters from LLVM-named stdarch builtins to GCC builtins. Other private attributes are only recognized, and some features remain stubs.

Two findings particularly illustrate why source inspection matters:

- The commit described as legacy const-generics support implements a real const-call transformation, but its attribute reader recognizes **`rustc_args_required_const`**, not **`rustc_legacy_const_generics`**. The tested generic shim works; the actual legacy spelling and an ordinary 1.49 required-const argument fail focused probes. The mechanism exists, but the compatibility claim needs narrowing.
- ADT const values are **not wholly unsupported**. The available compiler executes struct- and enum-valued const-parameter examples and rejects a mismatched enum value. Direct field access through a struct-valued const parameter fails; materializing that parameter as a typed local succeeds. Full structural-equality/`ConstParamTy` compatibility is not established. Separately, I found no evidence that the pinned mainline Linux Rust subtree requires ADT const parameters at all.

Both `phil/libcore-dev` branches contain relevant unmerged work. Their current tips have four and eleven branch-only commits respectively. Earlier development work has also reached master through rebasing/cherry-picking: exact patch-ID comparisons confirm several examples. The newer branch adds useful bound-scoping, substitution, impl-selection, and pattern fixes, but also carries experiments that must not be counted as completed semantics. In particular, commenting out a dereference assertion does not establish a correct dereference result.

Infrastructure is neither absent nor complete. Three small existing two-crate tests compiled, linked and ran in this audit using the available binary. However, metadata is currently an **AST-text export/reparse design**, not serialized typed HIR; a small exported-macro round trip fails because the exported definition is emitted twice. Procedural-macro loading exists, using gccrs-specific machinery, but Linux's host macro dependency graph is unvalidated. Debug information and scope-drop code exist; complete borrowing/drop semantics, kernel metadata/tooling, and configuration-dependent backend requirements remain separate concerns.

### Scope, terminology and confidence

“Merged” below means reachable from this repository's **local `origin/master`**, which equals HEAD. It does **not** mean every change has reached GCC's separate upstream release branches. No remote refs were refreshed. “Development-only” means present in a named inspected branch and absent from master; it does not establish whether its author considers it ready to merge.

The evidence inventory was assembled before this report: [inventory and qualifications](audit-evidence/2026-09-21/INVENTORY.md), [branch relationships](audit-evidence/2026-09-21/branch-relationships.json), [log diagnostic index](audit-evidence/2026-09-21/core-diagnostics.tsv), and [tracked test inventory](audit-evidence/2026-09-21/testsuite-inventory.txt). The testsuite contains 1,883 tracked `.rs` files: 1,486 compile, 317 execute, 47 alloc-source files, 13 borrow-check, 12 link, and 8 debug files. These are **file counts**, not independent feature tests or passing-test counts; diagnostic tests, copied library source, disabled tests and stage-limited tests need individual interpretation.

Exploratory runs used the existing `/home/philbert/workspace/gccrs-build/gcc/crab1`; its [hash and provenance limit](audit-evidence/2026-09-21/binary-provenance.txt) are recorded. I did not rebuild or establish its exact source commit. Consequently, results are labeled **available-binary observations**, while merged/development status comes from source and Git. Twenty-four selected repository execution tests and three positive ADT-const probes returned zero; five initially needed the audit's host link command corrected to `gcc -no-pie`. This is not a full DejaGNU run. No fresh whole-core or kernel build was performed.

### The intrinsic gap is concrete and independently actionable

The 107 rejected names consist of **85 atomic names and 22 others**. The atomic inventory includes compare-exchange/weak compare-exchange, exchange, arithmetic/bitwise/min/max RMW operations, fences, and some load/store spellings. Current gccrs provides load/store handlers for spellings such as `atomic_load_seqcst`, `atomic_load_acquire`, `atomic_store_release`, and relaxed variants. Rust 1.49 declares names such as `atomic_load`, `atomic_load_acq`, and `atomic_store_rel`. This is partly a historical interface mismatch. It is also more than aliases: the inspected tables do not implement the whole RMW/fence family, and [atomic handlers](gcc/rust/backend/rust-intrinsic-handlers.cc) explicitly restrict some signed-integer handling.

The other rejected names are instruction-prefetch variants, `breakpoint`, `pref_align_of`, `assert_inhabited`, `assert_uninit_valid`, seven volatile memory/load/store variants, five fast-float operations, `float_to_int_unchecked`, `exact_div`, `nontemporal_store`, and `ptr_offset_from`. The exact names are preserved in [core-summary.json](audit-evidence/2026-09-21/core-summary.json).

Registration alone will not suffice: each operation needs agreement among [intrinsic type checking](gcc/rust/typecheck/rust-hir-type-check-intrinsic.cc), [backend dispatch](gcc/rust/backend/rust-compile-intrinsic.cc), [handlers](gcc/rust/backend/rust-intrinsic-handlers.cc), [GCC builtin mapping](gcc/rust/backend/rust-builtins.cc), and const-call behavior where applicable. The inspected libcore-dev tip diffs do not supply these missing families.

### How close is `core`?

Parsing, expansion and resolution of a very large historical core/stdarch source surface are meaningful progress. Type checking now has enough machinery to expose complex library interactions, rather than stopping at every unfamiliar construct. The development reductions identify several tractable bug families, and some already have branch fixes.

However, **the current log is a censored observation**: it ends at `cmp`, before the remaining top-level visitation completes. Earlier on-demand resolution has touched some later modules, but that is not equivalent to finishing them. Intrinsic coverage, Debug derivation, drops, method/projection correctness, and subsequent codegen/import testing leave substantial unknown work.

The [core testsuite harness](gcc/testsuite/rust/core/core.exp) uses `-frust-compile-until=lowering`. In this checkout, [Session::compile_crate](gcc/rust/rust-session-manager.cc) checks that limit and returns **before invoking AST-to-HIR lowering**. Thus even a successful harness run is not evidence of full HIR construction, type checking, or a compiled usable core. Milestones should be reported separately: expansion/resolution, lowering, error-free type checking, codegen, metadata round trip, downstream linking, and behavioral tests.

### Important matrix qualifications

The [GAT where-clause probe](audit-evidence/2026-09-21/probes/linux_gat_where.rs) was reduced from Linux's `ForeignOwnable` shape, not from a feature name. It fails at `where` in the trait associated type. `parse_trait_type` in [the parser](gcc/rust/parse/rust-parse-impl.hxx) parses generics and bounds, then requires a semicolon. The development branch adds a default type before that semicolon, not an associated-type where clause. This supports **“GAT implementation with a missing required clause form”**, not “no GATs.”

The ADT-const experiments use `no_core` scaffolding and do not implement rustc's complete admissibility checks. See [struct selection](audit-evidence/2026-09-21/probes/adt_const_struct_selection.rs), [failing field access](audit-evidence/2026-09-21/probes/adt_const_struct.rs), [typed-local control](audit-evidence/2026-09-21/probes/adt_const_struct_control.rs), and [enum mismatch](audit-evidence/2026-09-21/probes/adt_const_enum_mismatch.rs). These establish existing capability and a specific failure boundary; they do not quantify how small the remaining full-feature implementation would be.

Some tests stop before type checking, expect errors, or are disabled. For example, `compile/auto_traits1.rs` is stage-limited, while `auto_traits2.rs` is not; the GAT work also leaves `compile/torture/traits18.rs.disabled`. Individual tests were read with their directives before being used as evidence.

## 3. Unstable/compiler-internal features required by core/stdarch

### The historical compiler/library contract

Rust 1.49's stable public APIs are not a self-contained description of the language used to implement its libraries. The authoritative historical [core root](https://github.com/rust-lang/rust/blob/1.49.0/library/core/src/lib.rs), [active feature table](https://github.com/rust-lang/rust/blob/1.49.0/compiler/rustc_feature/src/active.rs), and [builtin attributes](https://github.com/rust-lang/rust/blob/1.49.0/compiler/rustc_feature/src/builtin_attrs.rs) expose a larger contract. The checkout contains that source, so gccrs encounters the contract directly.

The 98-name [gate inventory](audit-evidence/2026-09-21/core-feature-gates.txt) includes language extensions, const-enabled library methods, target-specific extensions, documentation features, internal markers, already-stabilized gates retained historically, and mutually conditional bootstrap alternatives. Counting all names as language features—or as implemented gccrs capabilities—would be misleading.

| Contract encountered | Why core/stdarch needs it | What gccrs actually implements / remaining boundary |
| --- | --- | --- |
| `#![no_core]`, `#[lang = ...]`, prelude injection | Core defines Sized, Copy, arithmetic/deref/index/call traits, primitive operations, panic/formatting hooks and other foundations that user crates ordinarily import | Lang-item registry, lowering and targeted typechecker/backend use are substantial: [registry](gcc/rust/util/rust-lang-item.cc), [lowering](gcc/rust/hir/rust-ast-lower-base.cc). Some names are recognized but explicitly ignored, as the log warns. |
| `intrinsics` / `extern "rust-intrinsic"` | Layout queries, transmute, memory operations, arithmetic overflow, atomics, branch hints and low-level operations need compiler semantics | Signature checking, generic handlers, simple GCC builtins and CTFE interactions exist. The 107-name gap is a specific worklist, not evidence of no intrinsic implementation. |
| `rustc_const_stable`, `rustc_const_unstable`, `rustc_allow_const_fn_unstable`, `allow_internal_unstable`, staged API markers | Core exposes stable APIs while implementing them with privileged const/library features; it annotates stability and const-call permission separately | Attributes are registered/gated. `ConstChecker::is_const_extern_fn` treats any attribute whose name starts `rustc_const_` as evidence of a const external function and has a FIXME. This is a real compatibility mechanism, not complete rustc stability-policy enforcement. |
| Const generics before public stabilization | Core's arrays and generic library implementations need value parameters | General const types, substitution, array capacities, monomorphization and associated consts implemented. Stable 1.49 users could not yet use the eventual min-const-generics surface generally. |
| Const evaluation beyond basic const fn | Const library implementations use unions, pointer/layout operations, control flow and compiler intrinsics before all such operations are public stable | gccrs has a Rust const checker and a substantial GCC-tree evaluator. A feature gate in the library does not prove every operation works during evaluation; const/intrinsic fixes remain ongoing. |
| Explicit Fn traits, `unboxed_closures`, `rust-call` | Core declares callable traits and tuple-based call signatures; closures must satisfy them automatically | Callable resolution, tuple packing, closure types and codegen exist. Complex bounds and reference/capture behavior still expose bugs. Public closures being stable does not make explicit Fn implementation or this ABI stable. |
| `min_specialization`, default impl methods, specialization marker attributes | Core selects optimized implementations while retaining generic fallbacks, including iterator/library special cases | Minimum-specialization method selection and multilevel tests exist. Registration of `rustc_specialization_trait` / `rustc_unsafe_specialization_marker` is not proof of every coherence rule. |
| Auto traits and negative impls | Core defines Send/Sync/Unpin-related behavior and explicitly denies traits for selected pointer/wrapper types | Field propagation and negative checking landed in 2026. Full auto-trait soundness and borrow/lifetime consequences remain broader work. |
| `Unsize`, `CoerceUnsized`, `DispatchFromDyn`, custom self behavior | Slice/dyn coercions, pointer wrappers, Pin and boxed dynamic receivers need compiler participation | Array/ADT unsizing and Box dispatch implemented; modern arbitrary Receiver-chain lookup and general derived smart-pointer support are not established. |
| Associated type bounds | Core can state constraints on iterator-associated items without manually naming every intermediate parameter | Parser and typechecker tests now exercise nested associated bounds. Distinct from GATs; stabilized only in 1.79. |
| `extern_types` | Opaque FFI-facing types, including formatting internals, need names without normal Rust layout | Extern-kind ADT and C-void codegen implemented; not just tolerated syntax. |
| `decl_macro`, builtin macro markers and transparency attributes | Core provides language-integrated macros and newer declarative macro forms | Declaration/expansion and executable cases exist. Export/hygiene and metadata preservation are separate incomplete obligations. |
| `repr(simd)`, `simd_ffi`, `platform-intrinsic` | stdarch vector types must map to vector registers/layouts and compiler operations | Vector representation and 15 arithmetic/bitwise/comparison mappings exist. `platform_intrinsics.rs` explicitly comments out shuffles, insert/extract, reductions, gathers/scatters and many other operations; these are not passing tests. |
| `link_llvm_intrinsics`, LLVM-specific link names, `unadjusted` ABI | Historical stdarch source names LLVM operations, with signatures that may differ from GCC builtins | [Builtin map](gcc/rust/backend/rust-builtins.cc) includes 16 x86 LLVM-name adapters: rdrand/rdseed widths, addcarry/subborrow families and half-float conversions. Adapter kinds cover forwarding and out-pointer/value/status reshaping. This is actual code, but a small target-specific subset. |
| `rustc_args_required_const` and later `rustc_legacy_const_generics` | Instruction immediates must be compile-time constants; API compatibility can preserve ordinary call syntax after an implementation moves to const generics | Substantial argument-to-const-substitution/codegen machinery exists, but the current attribute dispatch conflates the two contracts. See focused finding below. |
| Target-feature gates and `#[target_feature]` | stdarch exposes instructions conditional on target architecture and enabled ISA features | Target cfg setup and safety checking exist. The attribute registry explicitly marks target-feature code generation unfinished. Compiling a test with `-mrdrnd` is not proof that a per-function attribute activates the ISA correctly. |
| `rustc_layout_scalar_valid_range_*`, nonnull/no-niche annotations | NonZero, references, pointer wrappers and MaybeUninit need layout/validity relationships | Recognition is not complete layout semantics. `assert_zero_valid` handler comments explicitly discuss limits without validity-range tracking; full niche contracts must be verified independently. |
| Generator/future/poll lang items, unsized-parameter gates, try-block/unwind extensions | Core includes definitions supporting language constructs and runtime conventions, whether or not ordinary library bodies exercise every lowering | Several lang items warn as unimplemented; general generator/state-machine support is not established. Do not count successful declaration processing as executable async support. |
| `compiler_builtins`, allocator/internal symbol markers | Freestanding libraries need control over generated helper symbols and default dependencies | Attributes and selected runtime hooks exist; complete kernel freestanding helper policy, allocator behavior and linked artifact compatibility remain separate. |

Current rustc explicitly classifies `intrinsics`, `lang_items`, `rustc_attrs`, `staged_api` and several related markers as **internal** in its [feature table](https://github.com/rust-lang/rust/blob/master/compiler/rustc_feature/src/unstable.rs). These should not be described as ordinary public features merely awaiting an announced stabilization date. Conversely, “permanently unstable” should not be asserted as a prediction for every unstable gate: the evidence establishes internal status, or current instability, not all future policy.

### Exact legacy-const finding

The implementation history is `c8da57d9d1c` followed by `36860cbddb7` (September 2026). The first registers the legacy attribute and fixes const casts. The second adds HIR call metadata, const-index parsing, argument folding/substitution, and exclusion of const-only arguments from generated runtime calls. That is significant implementation work.

However, [Function::get_legacy_const_generic_indexes](gcc/rust/hir/tree/rust-hir-item.cc) filters on `RUSTC_ARGS_REQUIRED_CONST`. The added regression [issue-3868.rs](gcc/testsuite/rust/compile/issues/issue-3868.rs) also uses that attribute on a const-generic function. The actual `RUSTC_LEGACY_CONST_GENERICS` name is registered but not selected by this reader.

Available-binary probes agree with the source:

| Form | Observation |
| --- | --- |
| `#[rustc_args_required_const(1)] fn foo<const N: usize>(x: i32)`; call `foo(10, 3)` | Compiles: the implemented shim. |
| Same generic function with `#[rustc_legacy_const_generics(1)]` | Rejects the second argument as excess. |
| `#[rustc_args_required_const(1)] fn foo(x: i32, n: i32)`; call `foo(10, 3)` | Incorrectly expects three arguments. |

[Sources and logs](audit-evidence/2026-09-21/cross-crate-legacy-results.json) are preserved. The third form matters to **this exact 1.49 stdarch**: `_mm_blend_epi16` in [x86/sse41.rs](libgrust/rustc-lib/stdarch/crates/core_arch/src/x86/sse41.rs) has an ordinary `imm8: i32` parameter annotated `rustc_args_required_const(2)`. A search found no `rustc_legacy_const_generics` occurrences in the vendored stdarch tree. Thus the right task is to separate historical required-const validation from legacy const-generic argument remapping, with regression tests for both—not to implement const generics from scratch.

### Stabilization of const-related pieces is not a single event

The historical broad `const_fn` and `const_generics` gates were eventually removed/split; their removal is not equivalent to stabilizing every operation they once covered. Selected relevant milestones from rustc's [accepted](https://github.com/rust-lang/rust/blob/master/compiler/rustc_feature/src/accepted.rs) and [removed](https://github.com/rust-lang/rust/blob/master/compiler/rustc_feature/src/removed.rs) tables:

| Capability | Stabilization / historical outcome |
| --- | --- |
| Basic const fn (`min_const_fn`) | 1.31 |
| Min const generics | 1.51 |
| Const fn unsizing | 1.54 |
| Const fn transmute and union access | 1.56 |
| Const-generic defaults | 1.59 |
| Const fn function-pointer basics, trait bounds, impl Trait | 1.61 |
| Inline const blocks | 1.79 |
| Const floating-point arithmetic | 1.82 |
| Mutable references in const contexts | 1.83 |
| Old broad `const_fn` / `const_generics` gates | Removed in 1.54 / 1.56; successor capabilities have separate histories |

This table gives Rust history, **not blanket gccrs conformance to each stabilized extension**. Library const APIs have their own per-item stability annotations; no attempt is made to assign one compiler-feature version to all the `const_*` library gates in core.
